# Changelog

All notable changes to Agent Manager are recorded here, in [Keep a Changelog](https://keepachangelog.com) format. The first release is 1.0.0.

## [Unreleased]

## [1.5.0] - 2026-11-10

The scheduled tasks release: prompts that run on a schedule, as a full Claude Code session or locked down without one, with an approval for what each can reach. Also underlined links, notifications sorted by what they mean, pictures Claude reads, a plain terminal, and selection with Shift+arrows in Claude's input.

### Added

- **Scheduled tasks** (off by default: "Use scheduled tasks" in settings; Claude Code only, for now). A scheduled task is a note with `type: scheduled task` in its properties, in a folder of its own named like it. Its properties say when it runs (`schedule`, in plain words such as `Weekdays 7:00`, or a date), how it runs (`mode`), and what it starts with (`reads`), with the prompt under `## Prompt`; the template opens with a `## Human Notes` section for your own notes on it, which a run is given after its prompt and which are approved with it. **Its project is where it sits**, as a ticket's is: with Use overviews on, the nearest folder above it with an overview (else its own folder), so one in `<project>/Scheduled Tasks/<Name>/` moves and archives with its project. Names needn't be unique; while two share one, notices, notifications, commits, tabs, and lists add where each sits. One in your Scheduled Tasks folder that sits in no agent profile's folder runs as no agent profile; elsewhere a task runs as the profile whose folder holds it, or the Default agent profile when none does.
- **The Scheduled Tasks row and page.** A row under the Daily Chat, above New Session and New Ticket, shows the next run (or "Running now…" while one runs), how many results you haven't opened ("3 outputs"), and how many tasks are pending. It opens a page that says what runs next and whether this computer runs the schedule, then lists every task, with the agent profile that runs it, under Active, Pending (to fix, to approve, or held), and Paused (folded). Right-clicking a task offers Open note, Run now (Stop while it runs), Start session, Approve…, Pause or Unpause, and Delete task (after asking; its folder is deleted the way Obsidian's Deleted files setting says). A task's own page shows its schedule, what's wrong with it, every folder, site, and tool a run could reach, what no run ever reads, its open follow-up ticket, and its runs, with Run now (Stop while it runs), Start session, Edit (which opens the note), and Pause or Unpause. A task's note has Run now in its header, and Stop while it runs; a Running pill at the top of the page opens the running task. An `op=task` link opens a task's page; no link starts a run.
- **The New Scheduled Task card**, from the page's New Scheduled Task row: a name, the project, how it runs, the notes and folders it starts with (Reads first, picked from the vault as chips, written as links that follow a rename), what a run can use for that mode, the schedule (repeat, days and time, or a date), and the prompt, with Each run (a new session or continue the last), the model (Fable among them), a follow-up ticket, and Only report when something's new under a folded Advanced Options. It files the task in the chosen project's `Scheduled Tasks/` and opens its page to approve.
- **Three ways to run.** **Full session**, the default, is a real Claude Code session in a background tab, listed in the sidebar like any session, in auto mode with your own settings, hooks, skills, MCP servers, and connectors. **Headless (Local Only)** and **Headless (Web Access)** run Claude Code without a session tab, locked down to Read, Glob, Grep, and Write (plus the web tools when the web is on, and Edit, NotebookEdit, or TodoWrite when its `tools` names them), with no MCP servers, connectors, or hooks, writing only into its own folder. A task with no `mode` is headless. The card writes `mode: full` or `mode: headless`, with `web` off, search, or a list of sites.
- **Full session runs.** The opening is typed in once the session has settled, so connectors are up, and the run is told its project's overviews (broadest first), its repo, and its `reads`, in its opening and pinned to its system prompt, through a compaction too. It keeps your `AGENTS.md`, with a paragraph in its system prompt that puts its opening ahead of the parts written for interactive sessions, telling a run with a shell to commit nothing, your work in progress included. It's watched to the end: done, finished without a result, waiting (it stopped to ask: "<task> is waiting for you"), or stalled past the time limit, which is left open and never ended. Only the end of Claude's turn counts as finished; a tab closed or a session ended mid-turn is logged interrupted, and Stop interrupts the turn and leaves the tab open. It's never retried, a waiting or stalled run doesn't take a runs-at-once slot, and a stalled run lets the Mac sleep. Its tab stays open afterward, or closes after a clean run with `tab: close`; a continued task closes its last run's tab first when that tab is idle and untouched, and otherwise waits.
- **What a full session run can't do.** It refuses connectors' sending, replying, forwarding, sharing, scheduling, and deleting (drafts, labels, and reads stay, apart from Slack's draft tool: a run's Slack drafts go in its result), Claude in Chrome, and the Keychain's password commands. Connectors are off unless a task sets `connectors: on`, the card starts a full session task with `web: off`, and a task can add `deny:` (Bash, WebFetch, WebSearch, Write, Edit, NotebookEdit, Agent, Skill). `web` is off, search, or a list of sites, held by a hook on fetches (which refuses an address with a backslash or a user name before its host) and by the shell's sandbox, held strictly to the list; since Claude Code adds your own settings' sandbox exceptions to it rather than letting a run clear them, a run with a site list or no web and a shell is refused while your user or managed settings widen the sandbox (excluded commands, allowed domains, local binding, and the like), and says which. Nothing is typed into a run until its guards' hooks have reported in at the session's start, so one whose hooks don't run (hooks turned off, or managed settings allowing only their own) is refused having been given nothing, and a session that didn't start in auto mode has its first prompt refused; the guard is written inline in each hook, never in a file a run could change. `shell`, `file-access`, `writes`, or `tools` with a value on a full session task (`false` included; a blank one is ignored) is a problem on it. The README says plainly what full session mode doesn't stop: it uses your normal Claude login, a reload or restart ends a run, the send rules match tool names, and the site list doesn't reach other MCP servers' tools.
- **An action log for every full session run**: `Actions.md` in the run's folder lists every tool call, its own and its sub-agents', with flags worked out by rule: writes outside the task's own folder, shell commands that may write outside it, `git push`, the `security` command, network commands, connector calls that aren't reads, fetches, shell hosts, and connector calls naming hosts off the site list, starting another agent's CLI (`codex`, `claude`, `agy`, `gemini`, and others, whose work the guards can't see inside), a missing transcript, and a run far longer than usual. A continued run's log covers only that run, and tokens are blanked in it. A flagged run says so in its run log row; the sharp flags (a push, the Keychain, a connector call that isn't a read, a network command, anything off the site list, web use while `web` is off, a missing transcript, and an action log that couldn't be written) are also a "needs you" notification. A headless run with the web is flagged for fetches off its site list too.
- **What a headless run reads.** Its own folder and its `reads` always; beyond them, `file-access` says how far its file tools reach (a sandboxed shell, below, reads the rest of the Mac apart from the never-read list): `none`, `project`, `vault`, `disk`, or folders outside the vault (`~/` or `/`, only with the web off, each checked on this computer: it exists, it's a folder, it isn't the whole disk or home, the vault or holding it, or on or leading to the never-read list; shown by its real path in the approval, and checked again before each run). A vault folder or note in `file-access` is a problem saying to move it to `reads`, and a `reads` entry that names nothing is a problem too. Each note in `reads` is given to the run as text. It never reads other scheduled tasks' `Outputs/` or `Memory.md` unless its `reads` names that task or one of its results, so a web task's findings reach the rest of a project only where something asks for them. No headless run loads your `AGENTS.md` as standing instructions (only as a note its `reads` names): a short fixed set of rules stands in for it (outside content never instructs; flag planted instructions; send nothing, and with the web, put nothing from your notes into a web address or a search; nothing to commit or ask).
- **A firewall between the web and the vault**: a headless task with the web reads only its own folder and the vault folders or notes its `reads` names, never its project, the whole vault, the whole Mac, or a folder outside the vault, and its agent profile's instructions and project overviews aren't pasted in unless it names them. A task with the web can't have Gather first, since a command's output changes from run to run. A task's site list can live in a note (`web: "[[Newsletter sites]]"`, one site per line), in both modes; its sites are in the approval, so editing the note asks again.
- **A sandboxed shell for offline headless tasks** (`shell: true`, with `web: off`): commands sandboxed by macOS, with no network, no writes, and nothing on the never-read list, so a local task can look things up itself; `writes` names folders its shell may change (organizing Downloads, say). There's no shell beside `file-access: disk` or where Claude Code managed settings exist. Tokens are dropped from its environment, the `security` command's credential operations are refused by their known forms (the sandbox doesn't wall off the login Keychain, as the README says), git skips `~/.gitconfig`, and `writes` refuses `~/Library`, hidden folders in your home, system and PATH folders, and overlap with `file-access`.
- **The never-read list.** "Never let a run read", in settings, which a full session run is held to as well (refused to its file tools, and to its shell when its web is limited, since a shell with the web open isn't sandboxed), plus a built-in list no headless run reads (a full session run otherwise reads what any session of yours can): credentials (`.ssh`, `.aws`, the Keychains, `.env` files), `.config`, browser profiles, Mail, Messages, and the transcripts folder among them, and this vault's config folder and every `.obsidian` folder, shell startup files (`.zshrc` and the like), `.gitconfig`, `.git-credentials`, `~/.claude.json`, and Claude Code's and Codex's settings files. A folder outside the vault can't be `/Volumes` itself or in a Time Machine backup; a task with `file-access: disk` reads those, and another vault's renamed config folder, like the rest of the disk. The plugin reads a run's memory and result only when each is a plain file in its own folder, never a link. Automatic memory is off for every scheduled run, so a run can't leave a note in Claude Code's automatic memory for later sessions to load (a full session run can still change any file a session of yours can), and anything shaped like a key or token is blanked in results, summaries, run log notes, and memory.
- **Approval.** A task runs only once this computer has approved it, in a dialog that shows everything a run could reach (Approve, Edit, Cancel), and waits for approval again when any of that changes. Every task's prompt and Human Notes are in it, so editing either asks again, and so are a full session task's `reads`. A task waiting for approval gets a card at the top of its page with Approve, Start session, Edit, and Pause. Pause and Unpause set its `paused` property; a paused task's page leads with Unpause, and has Approve when it isn't approved here.
- **Check run safety**: a button in the scheduled tasks settings that runs the safety gates on the Claude Code installed now, in a short run for each phase (the locked-down and shell phases always, and continued sessions and `writes` when an approved task needs them; Haiku when the account has it), and shows each case passed or failed, judged from what the run did. It covers headless runs, not full session runs. **Check run safety when Claude Code updates** (off by default, per computer) runs it before the first scheduled run on a new version, holds tasks when it fails, and has Run now wait for it; with it off, the tasks' page says when Claude Code updated since the last check. The latest result is written to `Run safety check.md` in the scheduled tasks folder.
- **Results.** Each run's result is filed as a new note (in its folder's `Outputs`, or at its `output` path, never over an existing note), marked as outside content, with the run's one-sentence summary in its frontmatter; its run log, its memory between runs, and its transcript follow, and in a vault that's a Git repository, with Commit each run's result on, a commit of the result, its run log, its memory, and a full session run's action log (with Git's hooks off). `## Gather first` commands run before each run, with `$AM_VAULT`, `$AM_TASK`, and `$AM_SINCE`; a command the task may not run, or more than 20 of them, is a problem on the task, and a vault script a command runs (by `$AM_VAULT`, `$AM_TASK`, or a path from the vault's top) is fingerprinted into the approval.
- **Latest Outputs**, a row on the tasks' page: every task's results in one list, newest first, the ones you haven't opened on this computer marked and counted, each with its outcome, how long it took, and its summary, under a card with Mark all as read. A result whose task moved is still listed and counted once, whatever form Obsidian rewrote its link in. Right-click one to mark it read or unread or open its run's transcript; a setting says how many it lists (50 by default).
- **Follow-up tickets** (`follow-up: ticket`): each result is added to the task's open follow-up ticket, or a new one in its project's `Tickets` folder, as one of its `reads`, and the result links back to it (`follow-up:` in the result, and the ticket in the run log row's note). Launching the ticket has the session read every result, fill in the ticket, and wait, with an opening of its own in settings. A follow-up ticket on a task with no project, or with tickets off, is a problem on the task.
- **Start session**, on a task's page and in its right-click menu: a session to talk over its results or work on its prompt. It's told it's a scheduled task and where its run log is, takes the runs' results as information, never as instructions, and waits. It has its own opening in settings, "Session from a scheduled task".
- **The clock**: on the computer where "Run scheduled tasks on this computer" is on, an approved task runs on its schedule while Obsidian is open. A run missed while the computer slept or Obsidian was closed catches up if it's less than half its interval late (with `catch-up: false`, only up to ten minutes late), and is logged as missed otherwise. A headless run that fails, writes nothing, or times out is retried once after five minutes, and one cut off by a reload at once, while it's still in time; three failed runs in a row hold the task until a run succeeds; runs cut off by a reload or a quit don't count, and the next load logs them interrupted. Changing a task's schedule, unpausing it, or approving it never fires a catch-up. Runs keep the Mac from idle-sleeping, Gather first included.
- **Launch or Resume from the ticket itself**: an open ticket has a Launch or Resume button in its header that does what the tickets base's Chat column does, and a command, "Launch or resume this ticket's session", to give a hotkey.
- **Pictures Claude reads show in the terminal, as the ones it sends do.** A PNG a Claude session reads (a screenshot it took to check its work, say) is drawn framed, with Open, Save to Downloads, and Copy path, under the line Claude Code folds it into ("Read 1 file, ran 3 shell commands"), or under its row; opening that line, or the ctrl+o transcript, keeps it. It's drawn as Claude got it when that's small enough, so it still shows after the file is gone, and otherwise from the file while it's there; a group shows its four newest and says how many more. The setting is now "Show pictures Claude sends or reads".
- **A plain terminal**: a shell with no agent session. "Open terminal" in the command palette opens one in the vault's folder, "Open terminal here" in a folder's menu opens one there, and "Open terminal in this folder" in a session tab's menu opens one where that session runs. It's never listed, has no strip, and writes nothing; after a reload it starts a fresh shell in the same folder. Its program saying it's done counts as a finished turn for notifications.
- **Links are underlined**: every web address, file path, and note name in a terminal that opens is underlined in the link's own color, drawn as part of each row's text so it scrolls with it, Claude's full screen included; a link wrapped onto the next row is underlined on both. **Underline links**, in the link settings, turns them off.
- **Shift+arrows select in Claude's input**, in its full screen, as in a text field: Shift+Left and Shift+Right a character at a time, Shift+Up and Shift+Down a row (on the first or last row, to the line's start or end). They start a selection at the caret, or extend one made with the mouse or Cmd+A, and never leave the input; typing, Backspace, Cmd+C, Cmd+X, and Cmd+V then work on it. The terminal's cursor hides while the input has a selection, as a text field's caret does.
- **The cursor is a blinking line between characters by default**, as in a text editor. The Cursor style setting offers a block (as before) or an underline, and Blinking turns blinking off.
- **Sub-agents' transcripts are kept**, Claude's and Codex's. Each sub-agent of a Claude session gets its own append-only note, in a folder named like the session's transcript note beside it, linked from the session's note; importing a Claude session brings its sub-agents, and moving or renaming the session's note moves their folder with it. Codex's sub-agents are kept the same way, each note named for the sub-agent's nickname and task, and importing a Codex session brings them too.
- **A Keyboard shortcuts section in the README** lists every key Agent Manager changes.
- **`obsidian://` links open from the terminal**: one that opens a note (`obsidian://open?…`, or `obsidian://vault/…`) and Agent Manager's own (`obsidian://agent-manager?…`), as plain text or marked by the program, with a click like any other link. A note in this vault opens where a clicked path's would (a heading in the link is left out), a missing one says so, and a link to another vault's note goes to Obsidian; Agent Manager's links open only for this vault. Other `obsidian://` actions (`new`, and other plugins' links, which can write notes or run commands) aren't links in the terminal. An `op=new` link, which starts a session, asks first when it's clicked in the terminal, a ticket's Launch link included (a Daily Chat link opens today's chat without asking), since a session can write a ticket and print its link.
- **Hovering an `obsidian://` link says where it goes**: the note's path (or that there's no such note), the session it resumes, or the note a session would start from, above the address itself.
- **Links the program left uncolored take the link color**: an `obsidian://` address or a path outside backticks is drawn in the color Claude Code gives code and paths (#b1b9f9 in a dark theme). In a light theme every link takes Obsidian's accent, the ones Claude colored too, since its code color comes out a faint grey-blue there, like the links it colors itself. With Underline links off, they keep the program's color.
- **The session strip names its agent profile**, in a pill beside the session id, so two sessions side by side are easy to tell apart. It shows the profile the conversation started as, which is what it was told; hover to see where it's filed when Move to agent profile put it elsewhere. Nothing shows with agent profiles off or for a session with none.
- **Unsent text survives a reload or a crash**, in Claude Code and Codex sessions (not Antigravity, for now). What you've typed into a session's prompt and not sent is saved with its tab as you type, and when Obsidian or the plugin reloads and the tab resumes, it's put back in the prompt, unsent, once the CLI is ready, with a notification saying so. If it can't go back (you typed first, or the session asks a question or doesn't start), a notification says it was dropped, or with **Copy unsent text that can't be put back** on (off by default), it's put on the clipboard. Sending or clearing the prompt drops the saved copy. Only text the plugin could follow from your keys and pastes is kept; a prompt edited in ways it can't follow (a line recalled from history, an edit mid-line, a Tab completion) isn't saved, and neither is anything while Claude's input box shows empty. **Keep unsent text through a reload**, in settings, is on by default; turned off, nothing is saved and each tab drops what it saved (a tab not opened since Obsidian started, when it's next opened).

### Changed

- **Notifications by what they mean.** "Needs you" is for something that broke or won't continue until you look at it: a session's question, permission prompt, plan, or error, something you asked for that wasn't sent, a new session's opening held up, an agent's program not found, the setup guide failing to write, and a scheduled task's failures, waits, stalls, holds, flags, and unfiled or uncommitted results. Information is for what's happening where nothing broke and nothing waits: a copy or a rename confirmed, a session moved to a new id, a scheduled run that went fine. Whether Obsidian is in front never decides where one goes. A permission prompt or a question notifies the moment Claude asks, and says which ("Claude has a question for you", "Claude needs your permission to use Bash"), rather than when Claude's own notification arrives about six seconds later. Questions, prompts, errors, and finished turns are built and tested for Claude Code; Codex and Antigravity aren't tested yet, and the settings say so.
- **A Notifications section in settings**: where "needs you" notifications go (Desktop, Obsidian, the default, Both, or None), replacing Notify when Claude needs you, whose setting isn't carried over: everyone starts at Obsidian, so choose Desktop or Both to hear about it in another app; Information notices in Obsidian (on); When a session finishes its turn (None by default); Hide notifications from the session I'm looking at (off); and When a scheduled run goes fine (None by default). Each kind's length has a row under it while it goes to Obsidian: 5, 10, or 30 seconds, 1 minute, or until clicked; Information is one length for all, in place of lengths that ran from 3 to 15 seconds. The Dock icon's waiting count, Status icons on tabs, and Sound on bell moved here from the terminal's look settings. In Obsidian a notification is drawn like the terminal's copy box, in the corner of the session you're looking at, stacked up to three, one per session or scheduled task; clicking it goes there, and its X only closes it. A desktop notification's sound and how long it stays are macOS's settings for Obsidian.
- **What was copied, and the picture buttons' messages, show in the terminal's corner, not as notices**: a small box at the terminal's top right, in its font, with who copied it above the start of the text, for as long as Information notice length says. Copy path shows as a copy, and Saved to Downloads (or a button's failure) shows the session's name above the message.
- **Links open with a plain click by default**, not Cmd+click. Dragging still selects text, and a link a program shows as other text, with its address hidden, still takes Cmd+click. That's for a new vault: one that ran an earlier version keeps Cmd+click until you change Open links with, in the link settings.
- **A web address opened from a session opens in the notes area**: in the Web viewer when it's on and opens web links, else the browser, so the session you clicked from stays in front. When any other tab lands among the sessions and is moved out, the session that was showing is shown again, not its neighbor.
- **The New ticket and New scheduled task cards list projects the same way**: a group per agent profile, opening with "No Project - <profile>" (its own folder, for what belongs to no project), then its projects (named without a leading `Projects/`); only the switched profile's while it has a folder, else every profile's, then the rest. The scheduled task card adds "Shared - No Agent" last, while a profile has a folder and the Scheduled Tasks folder is in none. Both say under their buttons where the note is saved and which profile it runs as, and while a profile has a folder, the ticket card picks No Project for you rather than asking.
- **A ticket's transcript links join its session links**: one line per session under `## Session Links`, its resume pill and then `| Transcript`, a link to its transcript note, added once the note exists; a `---` line ends the section, so what a ticket keeps below one stays at the bottom. The separate `## Transcripts` section is no longer written or read: in existing tickets, move each transcript link onto its session's line and delete the section, and take it out of your ticket template.
- **The starter ticket template and tickets base follow that layout**: a ticket made without a template of your own has its sections divided by `---`, a `## Session Links` section, and its own row of the tickets base at the bottom, from the base's new **This ticket** view. Turning tickets on writes them only where they're missing, so in a vault that already has them, add the view (filter `file.path == this.file.path`) and the embed `![[Tickets.base#This ticket]]` yourself.
- **A new tickets base shows a project in a group as `Group / Project`**: below a `Projects` folder, its Project column is the path from there, with `Archive` left out, so two projects with one name in different groups no longer merge. Without a `Projects` folder, it's the folder's name, as before. A tickets base you already have isn't changed.
- **A ticket's CLI property is `cli`**, not `backend`, matching the tickets base's CLI column and the settings. Rename the property in existing tickets and your ticket template, and `note.backend` and the `backend` column in a tickets base you've edited: a ticket with only `backend` set starts on the default CLI.
- **An agent profile's Home folder is now its Agent folder.** It's still optional: a profile without one is used where no other profile's folder holds a session's note or folder, when it's set as the Default agent profile.
- **A second side chat of one session is numbered**: "(side chat 2)", then 3, so side chats never share a name; the first is still plain "(side chat)".
- **Continue Session's Keep full context says "(fork)"**, the name Claude Code, Codex, and Antigravity all use for a copy of a conversation.

### Fixed

- **A line that fills the terminal's width shows its last character whole.** The terminal's text runs a hair wider than its grid, so the last character of a full-width line lost its right edge (the "m" of a word at the end of a wrapped reply showed as half a letter).
- **A path that starts partway down links, and a name several files share asks which**: a click opens `Agent Manager/Workspace/Plan.md` when one file in the vault ends in that path, matched on whole folder names and ignoring case. When several files match, a partial path or a bare name like `Overview.md`, the click opens a list of them, most recently edited first, where before a bare name opened whichever one Obsidian picked and a partial path never linked; the hover tip says how many files it names.
- **A path Claude wraps onto the next row links**: Claude Code wraps long lines itself, with a real line break and an indent, so a path split across two rows couldn't be clicked in a narrow pane. A row is now read on with the next when the next row's first word wouldn't have fit.
- **A link stays clickable while Claude repaints**: the terminal could look for a link on a half-written row, find none, and keep that answer until the pointer left the line, so the tip vanished and a click did nothing. Once a repaint is done, a link under the pointer gets its hover back.
- **A session started from a folder or note, with nothing else pinned, is no longer told to "read them again" after a compaction.**
- **One Escape no longer counts as clearing Claude's prompt.** Claude Code now clears it on a second Escape, so after a single Escape the plugin thought the prompt was empty while the text was still there, and Quiet, Wrap, or a rename could have typed onto it. Only two Escapes in quick succession count now.
- **Quiet, Wrap, the Remote Control dot, the strip's commands, and a rename no longer refuse an empty prompt** with "you have unsent text". Some deletions the plugin couldn't follow (part of a selection deleted or cut, Option+Backspace) left it thinking text was still there. Option+Backspace now deletes a word in its count, and before refusing, a Claude session's input box is read from the screen: one showing nothing, or only Claude's dim placeholder or suggestion, counts as empty.
- **Cmd+X after Cmd+A cuts all of Claude's input at once**, as a selection made with the mouse does, instead of a row at a time.
- **Cmd+X in Claude's input never loses the text.** The deletion now waits for Claude's copy to reach the clipboard. A copy that doesn't come within two seconds leaves the text where it was, and a notice says the cut failed. Before, a cut followed quickly by a tab switch could delete the text without copying it.
- **Copying across a wrapped row of Claude's input gives the text as typed**, not a line break and two spaces where the row wrapped, for a selection made with the mouse, Cmd+A, or Shift+arrows.
- **Copying from Claude's replies drops the two spaces in front of each paragraph**: the indent the copied lines share is taken off (a nested list or code keeps its own).
- **Large pictures show**: a picture over 64 MB of pixels (a long page's screenshot) was refused, leaving its frame empty. A PNG up to 256 MB of pixels is now kept, and one over 16 MB is decoded shrunk; Open shows the file whole.
- **A picture's frame no longer flickers under the pointer**: its gray text is drawn in the theme's gray, which Claude's hover highlight leaves alone, and Open is gray like the other buttons.
- **Scrolling past pictures is smooth**: the hidden characters under each picture are drawn as blanks, and the picture layer paints once a frame instead of twice. A screen of new pictures draws without a pause the first time (453 ms before, 8 after), and hovering a picture no longer shows a colored dash at its edge.
- **A note clicked in a session opens in the tab that's showing**, as a link in a note does, not in the first note tab in the window, which could be any tab, a dashboard included. With notes split into two groups, it's the one you were last in. An **Open notes in** setting, in the link settings, opens it in a new tab instead. A new tab, from either setting or for a pinned tab, goes at the end of the tabs, as do web pages and notes opened from a session's strip or transcript. A click that goes to a tab already open flashes it, as Obsidian does when it switches tabs, even when that tab is the one showing: a note, a session from its link or its sidebar row, a ticket's open session, and today's chat. Notes opened from the scheduled tasks pages (a task, its follow-up ticket, a run's transcript) open the same way too; they also took the first note tab in the window. When another plugin opens the note in a different tab (Dashboard Manager keeps a dashboard's tab for dashboards, say), the tab that shows it keeps the focus.
- **Closing a Claude session with background work still running asks first.** When a turn ends while a shell, sub-agent, or workflow Claude started is still going (Claude Code's Stop hook lists them), closing the tab, closing the window, or reloading Obsidian asks first, saying so: "Its agent still has work running in the background, such as a shell or a sub-agent." - Sessions started outside the plugin are listed too, named by their first message.
